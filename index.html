Operator Thesis

Approach to AI implementation in regulated enterprise environments

Key question

Where does time, effort, and coordination overhead actually accumulate?

Working method

Start with the people who do the work. Interview process owners, observe workflows directly, and build a simple model of what the current process actually costs before touching any technology.

Output

A ranked shortlist of workflow candidates with rough economics attached

Relevant example

Non-financial-risk teams—RCSA, TPRM, control testing—typically spend most of their time gathering the same information from different systems. The bottleneck is usually coordination and synthesis, not the analysis itself.

Key question

Who experiences the pain, who has the authority to act, and who must approve?

Working method

Stakeholder mapping from executive sponsor down through the process owner to the technology team. The key question is whether the person with the problem controls the budget or needs to build a case upward.

Output

A clear picture of who needs to say yes and what each of them needs to see

Relevant example

In regulated financial services, the CRO often sponsors, operations owns delivery, and the CIO gates the integration. Alignment across all three is usually a precondition for successful delivery.

Key question

What does this process actually cost in analyst time, cycle time, and downstream rework?

Working method

Document analyst hours, cycle times, error rates, and rework. A concrete baseline is what makes the business case credible and sets the performance target the implementation will be measured against.

Output

A documented baseline and a business case framing that connects current cost to investment threshold

Relevant example

A DORA evidence-generation cycle that ties up multiple analysts for several weeks has a calculable cost. That number drives the investment conversation before a single line of code is written.

Key question

Can a working demonstrator show that the most difficult piece actually functions?

Working method

Prototype the core workflow using realistic synthetic data. The most valuable demonstrators focus on the technically difficult parts—agent orchestration, integration, edge-case handling—and include an honest evaluation of what works and what does not.

Output

A working demonstrator with an evaluation of capabilities and limitations

Relevant example

The NFR platform and DORA control-line builds are structured around this: real agent orchestration, real integration patterns, real human-approval gates—evaluated against defined criteria.

Key question

Where does the data originate and where do humans stay in control of consequential decisions?

Working method

Map data flows from source systems through agent processing to write-back destinations. Every consequential output needs a human approval gate. The system should support human judgment, not bypass it.

Output

Integration architecture and documented control framework

Relevant example

In practice this means ServiceNow for records, Teams or Power Automate for approvals, and policy-engine verification before anything is written back to the systems of record.

Key question

Did it work, and can the same approach be applied to the next workflow?

Working method

Define success metrics before go-live. Measure cycle-time reduction, analyst hours saved, output acceptance rate, and human override rate. Then document the architecture and commercial template so the next use case starts from a better base.

Output

A measured result, a reference architecture, and a reusable template

Relevant example

One paid engagement should produce a documented baseline, a working integration, a measured outcome, and an architecture that makes the next workflow faster to implement—in the same organisation or a different one.

Evidence type

Enterprise workflow demonstrator

Problem

Regulatory change (DORA Article 12) is typically translated manually through policy, controls, infrastructure, verification, documentation, and audit evidence — a process that spans weeks and multiple teams.

Summary

A fully functional AI workflow demonstrator built around a real regulatory requirement (DORA Article 12). Uses synthetic and anonymized data throughout. Takes a regulatory input through AI-generated control updates, infrastructure proposals, policy-engine verification, compliance documentation, human approval gates, and a complete traceable evidence chain.

Architecture

Regulation → AI guideline proposal → AI control design → AI infrastructure change → policy verification → compliance work product → AI documentation → evidence package

Commercial relevance

Demonstrates the full architecture of an enterprise AI workflow: model integration (OpenAI o3 for regulatory reasoning, GPT-4o for infrastructure, GPT-4o-mini for documentation), an 11-state machine for end-to-end traceability, and human approval gates at every consequential step. Built using only synthetic and anonymized data.

Case study

Built around a DORA Article 12 regulatory requirement using synthetic and anonymized data only. The workflow routes through OpenAI o3 for regulatory reasoning and control design, GPT-4o for infrastructure code generation, and GPT-4o-mini for documentation. An 11-state machine provides full traceability from regulatory input to artefact. Human approval gates are embedded at each consequential decision point. The AI provider layer is abstracted so the architecture is not locked to any single model. Tests cover the full workflow including edge cases and human-override paths. The architecture reflects patterns from enterprise delivery experience.
